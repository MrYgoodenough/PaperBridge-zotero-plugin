## 当前产品判断

项目已超过演示原型，具备数字 PDF 翻译、保存、分屏、原生批注、任务恢复和非 macOS 自动更新的个人可用核心。下一阶段不宜继续用功能数量衡量成熟度：优先做到 **译文可信、凭据/阅读产物不因失败丢失、已支持平台能够复建和升级**，再扩展扫描件、架构和精确双向编辑。

当前四包体积：Linux 自带 **272.88 MiB**、local **236.71 MiB**；Windows 自带 **189.70 MiB**、local **178.31 MiB**。local 仅移除解释器，不是本地 LLM 或轻量插件。macOS 当前为独立 0.4.2；不能用历史 macOS 包统计或主线源码证明其可复建。

### 两个低成本、具体的可靠性缺口

- **凭据失败窗口**：`saveKey()` 先移除当前 realm 的旧登录项，再 `await addLoginAsync()`。新写入抛错时旧值已经丢失。这是静态可见的风险，尚未做真实失败注入；不把它与历史验收误触保存造成的密钥变化混为一谈。应直接修原函数的替换顺序/原生修改逻辑，保留有意清空语义，不另起凭据系统。
- **资源错误误分类**：本次直接使用生产代码中的两条字面消息核对，排版资源缺失和 tokenizer 缺失都返回 `startup`。该路径有确切复现，不代表资源错误分层已完整；仅需调整现有分类并补两条核心检查。

### 安全风险的证据等级

仓库历史声称“旧版解析安全问题已披露”，但没有具体公告、修复版本或受影响路径引用。本次 GitHub 全局 advisory 对 `babeldoc@0.6.4` 查询为 0，**不能证明安全**。发现的上游 [PR #566](https://github.com/funstory-ai/BabelDOC/pull/566) 涉及缓存目录校验，但已关闭且未合并；不能由此证明 PDF 可控利用或某个新版已修复。

应先限时核实来源、可达路径和修复版本，再决定是否直接迁移现有 adapter。已知 0.7.1 的捕获、保护对象及字体路线存在实际障碍，不能只改依赖版本，也不能宣称 0.7.1 自动等于安全版。核实出可利用漏洞则立即升为 P0；当前保持可信 PDF 使用提示，不以没有根据的安全主张推动大规模重写。
