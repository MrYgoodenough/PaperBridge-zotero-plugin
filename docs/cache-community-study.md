# DeepSeek 输入缓存调研与 0.2.1 改进

检索日期：2026-10-27。关注实际未命中 token 总量，不以增加重复内容来抬高命中率。

## 来源与适用结论

1. [DeepSeek 官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)：缓存默认启用；前缀必须与已落盘的缓存单元匹配。构建需要时间，按尽力原则运行。不同正文首次发送会带来新的输入。
2. [DeepSeek Harness 社区实测 #4749](https://github.com/deepseek-ai/deepseek-harness/discussions/4749)：把可变用户输入放在固定上下文之前会破坏跨请求的可复用前缀。可迁移的建议是保持固定部分在前，并保证字节稳定。案例中的长会话命中率不能直接套用于逐段论文翻译。
3. [DeepSeek Harness 重启前缀变化报告 #8529](https://github.com/deepseek-ai/deepseek-harness/discussions/8529)：重建 system 前缀可能导致首个请求大量未命中。插件采用版本固定的 system 文本，并记录其哈希供核对。
4. [Codewhale 原作者问题记录 #3738](https://github.com/codewhale-hq/Codewhale/issues/3738)：时间戳、计数器、排序变化和动态元信息出现在请求前部时，会使共享前缀缩短。插件的实际请求不包含这些动态字段。

## 本项目复盘

0.2.0 使用 BabelDOC 默认批次，每批约超过 200 token 或 6 个段落便提交。每个请求重复携带较长的格式说明、示例、布局标签、公式提示和章节上下文。三页实测共 12 个请求：前四个请求未命中，后八个各命中 256 token；总输入 10,942，命中 2,048，未命中 8,894，输出 3,958。

记录中没有“译文相同”回退，因此这轮输入放大的主要因素已转为小批次和重复提示，而不是上一轮的图内乱码回退。

## 0.2.1 实施

- 固定精简的 system 指令；统一 JSON 协议。可变正文只放在 user 消息尾部。
- 保留文档标题作为一致上下文，移除不断变化的最近章节标题、重复示例、布局标签和冗余公式说明。公式和样式标记仍严格核对。
- 将普通段落批次改为约 1,200 token / 12 段；保留原引擎的跨页、跨栏和公式处理。输出上限相应调整为 8,192 token，思考模式关闭。
- 实际 API 并发上限为 2，不发送空的预热请求。
- 增加按文档、模型、目标语言和文本内容索引的本地段落缓存。改变批次顺序或重启后可直接复用译文。
- 缓存与任务状态目录独立于运行时版本，升级 XPI 时继续保留。
- 记录每次 API 的真实命中/未命中用量、固定前缀哈希和段落数量；设置页展示最近任务用量，本地完整译文复用显示 0 次 API。

## 验证

固定前缀、段落重新分组、重启缓存复用和公式占位符拒绝写入等单元测试已通过。使用旧三页译文做离线重放，8 个批次只需要约 4,972 个估算输入 token，未调用 API。实测对比记录另见 `cache-benchmark-0.2.1.json`。

## 实际 A/B 结果

同一论文第 2–4 页、同一 `deepseek-flash` 模型，均从完整 XPI 中运行：

| 指标 | 0.2.0 | 0.2.1 |
|---|---:|---:|
| API 请求 | 12 | 10 |
| 总输入 token | 10,942 | 5,610 |
| 缓存命中输入 | 2,048 | 896 |
| 未命中输入 | 8,894 | 4,714 |
| 输出 token | 3,958 | 3,843 |

未命中输入减少 47%，总输入减少 48.73%。由于移除了大量重复提示，命中率本身由约 18.7% 变为约 16%；输入费用应结合实际命中与未命中数量计算，不能仅按命中率判断。新输入中的主要剩余部分是首次翻译的正文。

十个实际请求的 system 前缀哈希全部一致。没有为构建缓存额外发送空请求。实际测量中两次编号校验触发了回退；已补充数字字符串编号兼容及单元验证，未为此追加付费重测。

已另行启动一个进程，从 SQLite 读取同一文档的全部 26 个记录段落并改变其批次顺序，全部直接复用译文，0 次 API。
